Running several Kafka clusters from different vendors with Lenses

Confluent, MSK and open-source Kafka side by side: one view and one access model without forcing a migration.

{{ cover }}

The reality of large companies

Few companies have a single Kafka cluster. It is common to find Confluent in one area, Amazon MSK in another, open-source Kafka in a legacy project and sometimes IBM Event Streams. Each has its own console, permissions and way of operating.

The cost of fragmentation

For the platform team, every vendor is one more tool to learn and monitor. For squads, finding which cluster holds a topic is already a task. And for security, auditing access means stitching reports from several places.

What a single layer changes

Recent versions of Lenses connect multiple Kafka environments to a single pane. The team sees every cluster, topic and consumer in one place, applies the same permission and masking model and audits everything centrally, without changing where each cluster runs.

A bridge to consolidation

A single layer also helps when the decision is to consolidate. With visibility over what exists in each cluster, who produces and who consumes, migrating to a main platform, for example from MSK or Event Streams to Confluent with Cluster Linking, can be planned in waves with fewer surprises.

How to implement

Start with inventory: connect clusters to Lenses read-only and map topics, volumes and consumers. Unify the group model before enabling writes. Use that inventory as the basis for deciding what stays where and what is worth migrating.
